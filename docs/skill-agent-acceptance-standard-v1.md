# 派总 Skill / Agent / 工具入库与替换标准 v1.0
更新：2026-11-10

## 目标
用户每天把看到的文章、视频、Skill、Agent、网站和开源项目贴给 ChatGPT，默认触发“评估是否有助于现有生产链路”，不只是摘要或安装指引。
ChatGPT 负责问题拆分、工具调度、设计测试、保存证据、比较当前基线、提出最终“替换 / 补强 / 观察 / 淘汰”结论。不能宣称调用过没有权限的 Work、Codex 或 Mac 本地执行节点。

## 组织与执行
- **ChatGPT（总控）**：整理来源、识别业务目标、分派测试、核数和最终裁决。
- **Work（网页执行）**：实际需要操作网页登录状态和后台界面时使用；只在实际进入 Work 模式并成功运行后记录证据。
- **Codex（工程执行）**：安装、编写适配器、脚本、代码检查、测试和重构；按实际代码 commit / 运行日志记录。
- **隔离 CI**：测试公共开源源码，锁死 commit SHA，最小权限，不注入秘钥和私人资料。
- **本地 Mac / 视频服务器**：专属 TTS/GPU/剪辑/业务系统实测，在 Linux 上通过不等于 Mac 通过。

## 每个候选的标准文件
1. `source.json`：来源链接、原文快照或哈希、发布时间、许可证、版本 SHA。
2. `task.md`：解决谁的什么问题，原生产链路、输入、预期输出和验收阈值。
3. `run.json`：执行环境、程序、命令、退出码、开始结束、资源和成本。
4. `artifacts/`：输出文件（图片、HTML、MP4、脚本），保留内容哈希。
5. `qa.json`：正确性、完整性、画面、音频、版权与平台合规检查，不通过的证据。
6. `comparison.md`：同一输入与当前基线进行 A/B 比较：质量、速度、成本、可维护性。
7. `decision.json`：replace / assist / observe / reject；决策理由、风险、下一次复测条件。
8. `SOP.md`：通过验收后才形成标准岗位、触发条件、操作指令、失败降级与验收。

## 状态规则
discovered → inspected → test_pending → testing → tested_pass → integrated → regression_pass。
任何阶段可 blocked 或 rejected。正式“已验收”必须有可以核对的真实日志和实体产物，不能由模型凭描述推断。

## 业务替换规则
- 做到同等可用输出，至少有一项成本/用时/质量改善，其他关键指标不能退步。
- 对外内容必须过核数关、素材授权与平台政策关。
- 用户原有 HyperFrames+VoxCPM2+Canvas/GSAP+Chrome+FFmpeg 为口播基线；不能仅凭新项目能出 MP4 就替换。
- 允许吸收模块而不吸收整套框架；优先复用已跑通能力，减少系统数量。
- 标准化的是**结果型任务**，而不是“工具名单”。

## 第一份真实案例
项目：threerocks/article2media，v2.0.1，主线 SHA `5e752beaa7cd396804b732032ada482da6851e43`。
Linux GitHub Actions 实测：
- 普通 Markdown：公众号 HTML 与 3:4 原文卡片正常生成并通过逐块完整性校验；
- 有 `### 1. 标题序号`：主线代码两种格式均因原文账本口径错误验收失败；
- PR #2 的 SHA `03ee9bff32f9be5ad98ac1b4db4e4cfecc73b29a`：相同边界测试两项均通过（0 版式错误）。
证据：https://github.com/paivspai/paizong-agent-os/actions/runs/42726272107

**结论**：图文与公众号排版具有真实功能，修复版可作为模块候选继续接入；主线 2.0.1 原文路径存在 bug；语音、视频、Mac 速度、系统集成和发布链路仍未验证，不许标为全部通过。
